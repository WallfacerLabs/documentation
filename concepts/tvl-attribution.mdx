This page explains how to attribute vault deposits and withdrawals to your wallet, app or frontend so you can see the TVL you drive in [portal.vaults.fyi](https://portal.vaults.fyi). Use it if you build vault transactions (yourself or through vaults.fyi) and want reporting, or to qualify for fee-rebate programs where they exist. Attribution works by appending a short suffix to the transaction calldata. The suffix does not change what the transaction does: the user still calls the vault or protocol contract directly, with the same recipient, value and arguments.

## Two ways to enable attribution

| You build transactions with | What to do |
| - | - |
| The vaults.fyi Transactions API (`GET /v2/transactions/{action}/{userAddress}/{network}/{vaultId}`, rewards claim) | Nothing. Returned vault-call `actions[].tx.data`, when present, already ends with the suffix (approve calls are not suffixed). Native value-only deposits can omit `data` and have no calldata suffix. **Do not append it again.** |
| Your own transaction builder | Fetch the suffix from `GET /v2/transactions/suffix/{userAddress}/{vaultId}` and append it to `data` of every vault transaction you want attributed. |

Example: the vaults.fyi deposit payload for user `0xd8dA...6045` and vault `0xbeeff...8845` on 2026-10-23 ended with `232c5f404de80be3c7ef2001de2d09ce535a2a0fffc69deb`, exactly the value the suffix endpoint returned for the same pair.

## Get and append the suffix

`GET /v2/transactions/suffix/{userAddress}/{vaultId}` (header `x-api-key`).

- `userAddress`: the end user whose position should be attributed (not necessarily the transaction sender, so relayers and smart wallets work).
- `vaultId`: the vault's `vaultId` from `GET /v2/detailed-vaults`.
- Response: `{"suffix": "<hex without 0x>"}`. The observed suffix is 24 bytes (48 hex characters).
- Cost: 1 credit per call (see [Credits](/plans/credits)). Earlier versions of this page called the endpoint free; that was wrong.
- It needs an API key with attribution enabled. Without one it returns 400 ("API key does not have a transaction suffix configured") and you are not charged. It can't be bought keyless over x402.

Real response (2026-10-23):

```json
{ "suffix": "232c5f404de80be3c7ef2001de2d09ce535a2a0fffc69deb" }
```

Append it without another `0x`:

```typescript
// tx is the transaction your own builder produced for this user and vault.
const tx = { to: "0xbeeff2490FEffa212faC2f6553682C219E6a8845", data: "0x6e553f65..." as `0x${string}`, value: 0n };

const res = await fetch(
  `https://api.vaults.fyi/v2/transactions/suffix/${userAddress}/${vaultId}`,
  { headers: { "x-api-key": process.env.VAULTSFYI_API_KEY! } },
);
if (!res.ok) throw new Error(`HTTP ${res.status}`);
const { suffix } = await res.json();

const tracked = { ...tx, data: `${tx.data ?? "0x"}${suffix}` as `0x${string}` };
```

```python
import os, requests

r = requests.get(f"https://api.vaults.fyi/v2/transactions/suffix/{user_address}/{vault_id}",
                 headers={"x-api-key": os.environ["VAULTSFYI_API_KEY"]})
r.raise_for_status()
tracked = {**tx, "data": (tx.get("data") or "0x") + r.json()["suffix"]}
```

Rules:

- Append to **every** vault transaction you want attributed: deposits, withdrawals, redeems, claims. Attribution is per transaction; a transaction without the suffix is not attributed.
- Only `data` changes. `to`, `value`, `chainId` and the function arguments stay the same.
- Do not append twice. Payloads from vaults.fyi already end with the suffix.
- The suffix is deterministic for a given API key, user address and vault address (no nonce, timestamp or amount), so you can cache it. Vault IDs that share one contract address share the same suffix.
- For smart wallets and multicall, keep the suffix on the inner vault call: pass each vault call's `data` through unchanged. Attribution scans the whole transaction input, and the suffix must be generated for the address the vault sees as the depositor (for a smart wallet, the smart-account address, not the signer).

## What you need

- A vaults.fyi account and API key. Sign-up is self-serve at [portal.vaults.fyi/signup](https://portal.vaults.fyi/signup).
- The user's wallet address and the `vaultId` for each transaction.
- Access to portal.vaults.fyi to view attributed TVL (attributed TVL tracking in the portal is free).

## What the portal shows

The portal is a drill-down from total attributed TVL to single user-vault relationships:

| View | What it shows |
| - | - |
| 1. Overview | Total attributed net TVL, asset allocation, daily TVL chart |
| 2. Breakdown by protocol or curator | Daily attributed TVL per protocol or curator, with a table per source |
| 3. Vaults | Each vault receiving attributed flows: network, APY, AVO, net TVL |
| 4. Vault detail | Daily attributed TVL for one vault and the users contributing to it |
| 5. User detail | Attributed balance and transaction history for one user in one vault |

Metric labels used in the portal (descriptions are working descriptions, not official definitions):

| Metric | Working description |
| - | - |
| Net TVL | Current value of attributed positions in the vault |
| AVO (average value outstanding) | Average attributed value held in the vault over the selected period |
| Daily TVL | Attributed TVL per day |

You can track deposits, withdrawals, redeems, claims and other supported actions created by your integration; current attributed TVL by vault, protocol, curator and network; how much value stays in vaults after users enter; and which flows may qualify for fee-rebate programs where available.

Attributed TVL is available in the Portal ([portal.vaults.fyi](https://portal.vaults.fyi)), not through the API. Large partners can ask the team about API access.

## For curators and protocols

Send integrators this page so they can create a key, append the suffix to their existing vault transactions, and appear in portal.vaults.fyi. Once integrators tag transactions, you can see which partners route users into your vaults and how much TVL remains attributable to them.

Errors: a request without `x-api-key` returns HTTP 402 (x402 payment challenge), and an invalid key returns 401. Other status codes and the error body shape: [Errors](/api-reference/errors).
