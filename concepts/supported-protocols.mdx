This page lists the networks and protocols vaults.fyi covers and the exact identifiers the API accepts for them. Use it to build filters, validate user input, or check whether a vault supports transactions. As of 2026-10-23 vaults.fyi covers 80+ protocols (126 protocol IDs from `GET /v2/protocols`) on 22 EVM networks (`GET /v2/networks`), plus Solana vaults on the Beta SVM endpoints. These counts change; the reference endpoints below always return the live lists (REST, `x-api-key` header on `https://api.vaults.fyi`).

## Live reference endpoints

| Endpoint | Returns | Use the value in |
| - | - | - |
| `GET /v2/networks` | `[{name, chainId, networkCaip}]` | `network` path params; `allowedNetworks` / `disallowedNetworks` (send `name` or `networkCaip`) |
| `GET /v2/protocols` | `[{protocolId, name, displayName, product?, version?}]` | `allowedProtocols` / `disallowedProtocols` (send `name` or `protocolId`) |
| `GET /v2/assets` | Assets with `symbol`, `address`, `network` | `allowedAssets` / `disallowedAssets` (send the **symbol**; token addresses are not accepted and are echoed in `errors.unsupportedAssets`) |
| `GET /v2/curators` | `[{name, displayName, websiteUrl?}]` (155 on 2026-10-23) | `curators` (send `name`) |
| `GET /v2/tags` | 18 tag strings, for example `Liquid Staking`, `RWA` | `tags` |
| `GET /beta/svm/detailed-vaults` | Solana vaults (Beta) | — |

Unknown filter values never return an error: the response is HTTP 200 with fewer or no results and the rejected value in `errors.unsupportedNetworks`, `errors.unsupportedAssets` or `errors.unsupportedProtocols`. Unknown `curators` values are not echoed at all. Check `errors` and validate input against these endpoints. See [API conventions](/api-reference/conventions).

In a path, a bare chain id (`8453`) or an unknown name such as `ethereum` returns HTTP 400. In a filter, an unknown value returns HTTP 200 with the value echoed in `errors.unsupportedNetworks`. Solana is not a v2 network. Solana vaults, positions and transactions live under `/beta/svm/...` and use base58 addresses (`{vaultAddress}` path parameter).

**Default scope:** `GET /v2/detailed-vaults` and the `/v2/portfolio/*` list endpoints return only `base`, `mainnet`, `arbitrum` and `optimism` unless you pass `allowedNetworks`. A comma-separated list returns 0 results. `GET /v2/vaults` and `GET /v2/assets` have no default scope.

## Protocols

Each protocol entry has a lowercase `protocolId` built from its name and, where applicable, product and version. Real entries (2026-10-23, `GET /v2/protocols`, trimmed):

```json
[
  { "protocolId": "40acres", "name": "40acres", "displayName": "40Acres" },
  { "protocolId": "aave-collateral vault-v3", "name": "aave", "displayName": "Aave", "product": "collateral vault", "version": "v3" },
  { "protocolId": "aave-staked aave", "name": "aave", "displayName": "Aave", "product": "staked aave" }
]
```

`allowedProtocols` and `disallowedProtocols` accept either:

- a protocol `name` (`aave`) to match every product and version of that protocol, or
- a full `protocolId` (`aave-standard spoke-v4`) to match one product.

**A name matches every protocolId that shares it.** This is a silent trap: the request returns 200 and mixes products.

| You want | Send | Not |
|---|---|---|
| Morpho V1 (MetaMorpho) vaults only | `allowedProtocols=morpho-metamorpho` | `morpho` (also returns `morpho-v2` and `morpho-market`) |
| Morpho V2 vaults only | `allowedProtocols=morpho-v2` | `morpho` |
| Aave v3 vaults | `allowedProtocols=aave-collateral%20vault-v3` (the ID contains a space) | `aave-v3` (unknown ID: 200, empty `data`, echoed in `errors.unsupportedProtocols`), `aave` (matches 8 Aave protocolIds) |

Observed 2026-10-23 on Base: `allowedProtocols=morpho` returned 62 vaults (31 `morpho-metamorpho` + 31 `morpho-v2`); `allowedProtocols=morpho-metamorpho` returned exactly the 31 V1 vaults. Always take exact IDs from `GET /v2/protocols` and check `errors.unsupportedProtocols`.

protocolIds can contain spaces. URL-encode them (`allowedProtocols=aave-standard%20spoke-v4`) or let your HTTP client encode query values. If you pass `allowedProtocols`, `disallowedProtocols` is ignored (spec: "The parameter is ignored if allowedProtocols is specified").

```bash
# All Aave products on Ethereum mainnet (vaults with TVL >= 100,000 USD by default)
curl -s --get "https://api.vaults.fyi/v2/detailed-vaults" \
  -H "x-api-key: $VAULTSFYI_API_KEY" \
  --data-urlencode "allowedProtocols=aave" \
  --data-urlencode "allowedNetworks=mainnet"

# Only Aave V4 Standard Spoke
curl -s --get "https://api.vaults.fyi/v2/detailed-vaults" \
  -H "x-api-key: $VAULTSFYI_API_KEY" \
  --data-urlencode "allowedProtocols=aave-standard spoke-v4" \
  --data-urlencode "allowedNetworks=mainnet"
```

Protocol matching differs by endpoint. v2 detailed vaults, positions, `/v2/vaults` and beta advanced analytics match the protocol `name` or `protocolId`, case-insensitive. Beta borrow markets also match `name` or `protocolId`; beta SVM endpoints additionally accept the numeric protocol id. Beta fixed-term matches the protocol name only.

## Analytics-only vs transactional vaults

Every vault has market data (APY, TVL, fees, history, Reputation Score). Only some also support the Transactions API (ready-to-sign deposit, redeem and claim calls).

To check a vault, read `isTransactional` on its `GET /v2/detailed-vaults` or `GET /v2/detailed-vaults/{network}/{vaultId}` response, or filter lists with `onlyTransactional=true`. `transactionalProperties` tells you more:

| Field | Meaning |
| - | - |
| `isTransactional` | `true` if `/v2/transactions/*` can build calls for this vault |
| `transactionalProperties.depositStepsType` | `instant` or `complex`, as returned by the API |
| `transactionalProperties.redeemStepsType` | `instant` or `complex` |
| `transactionalProperties.rewardsSupported` | `true` if reward claims can be built for this vault |

An `instant` deposit can still involve two transactions (ERC-20 `approve`, then deposit). Always read the exact steps from `GET /v2/transactions/context/{userAddress}/{network}/{vaultId}` and execute every returned action in order; see [Transaction flows](/concepts/transaction-flows).

`instant` means the deposit or redeem finishes in one step without waiting; it can still take two transactions (approve, then deposit). `complex` means the flow has a waiting period between steps, for example `request-redeem` → wait → `claim-redeem`, `start-redeem-cooldown` → wait → `redeem`, or `request-deposit` → wait → `claim-deposit`. In other words, `complex` is a queued or asynchronous flow. To know when a queued withdrawal can be claimed, poll the transaction context until `currentRedeemStep` is `claim-redeem`.
